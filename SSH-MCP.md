# Личный MCP через SSH

## Подключение с нуля

Сотрудник получает от администратора одну готовую команду для своего терминала.
Шаги 1 и 2 выполняет администратор на Linux, шаги 3 и 4 — сотрудник на своём ПК.
Мастер входит в поставку `second-brain-20261123-ssh-setup-r2`. На сервере остаются
SilverBullet, мост и исходный клиент этой поставки.

### 1. Администратор запускает сервер

`TARGET` — абсолютный путь **установленного проекта**. Для первой установки
распакуйте проверенный runtime-архив отдельно от TARGET и пройдите [установку с plan и apply](INSTALL.md#входные-значения).
Обычный apply сам запускает службы. Для уже установленного совместимого сервера:

```sh
python3 -I -B "$TARGET/tools/install.py" start --target "$TARGET"
python3 -I -B "$TARGET/tools/install.py" status --target "$TARGET"
```

Убедитесь, что службы работают, и выдайте сотруднику личную учётку Second Brain
с доступом `write` в нужном пространстве. Личный SSH MCP требует серверного ядра offline.3.
Переход с более старого ядра описан в разделе «Подготовка на сервере».

### 2. Администратор один раз подключает SSH к проекту

На новой установке задайте `BRIDGE_DIR="$TARGET/ssh_mcp"`.
Если уже работает **r2 с ядром offline.3**, возьмите `SOURCE` из нового проверенного
архива и разместите три файла рядом внутри проекта. Для первого перехода используйте новый каталог:

```sh
BRIDGE_DIR="$TARGET/agent-ssh"
mkdir -m 700 "$BRIDGE_DIR" &&
  install -m 644 "$SOURCE/ssh_mcp/bridge.py" "$SOURCE/ssh_mcp/client.py" "$SOURCE/ssh_mcp/connect.py" "$BRIDGE_DIR/"
```

Для обоих вариантов выполните под владельцем проекта:

```sh
python3 -I -B "$BRIDGE_DIR/bridge.py" --prepare "$TARGET" --ssh-alias secondbrain
```

Замените `secondbrain` в аргументе `--ssh-alias`, если на рабочих местах используется другое имя SSH.
Команда читает внутренний порт из действующего `config/service.json`, создаёт
`TARGET/config/ssh-mcp.json` и печатает шаблон строки для `authorized_keys`, затем две команды подключения для сотрудников.
Подставьте вместо `PUBLIC_KEY` тип и открытый ключ сотрудника. Добавьте эту строку
в `authorized_keys` серверной SSH-учётки с доступом к мосту и конфигурации.
Для уже используемого ключа обновите его ограниченную запись. Подробности прав — ниже.

Пример записи в личном SSH config рабочего ПК (на Windows — в `%USERPROFILE%/.ssh/config`).
Подставьте реальное имя сервера, SSH-пользователя и путь к выделенному закрытому ключу:

```sshconfig
Host secondbrain
    HostName SERVER
    User SSH_USER
    IdentityFile ~/.ssh/SECOND_BRAIN_KEY
    IdentitiesOnly yes
```

Подготовьте запись для этого сервера в `known_hosts`, сверив ключ хоста по вашему
доверенному каналу.
Проверьте, что SSH может использовать этот ключ без интерактивного запроса.
Из вывода `--prepare` скопируйте сотруднику **целиком одну строку** под заголовком
`Windows (PowerShell)` или `macOS / Linux` через обычный доверенный канал команды.
Для стандартного имени `secondbrain` эти же строки уже собраны в файлах выпуска
`CONNECT-WINDOWS.txt` и `CONNECT-MAC-LINUX.txt`.
Эту строку можно поместить на внутреннюю страницу «Подключить Second Brain».
В ней уже указаны SSH-подключение и ожидаемые SHA256 обоих файлов. После обновления
`connect.py` или `client.py` сгенерируйте команду ещё раз и обновите страницу.

### 3. Сотрудник вставляет команду

Откройте PowerShell на Windows или терминал на macOS/Linux. **Вставьте строку,
которую дал администратор, и нажмите Enter.** Подойдёт любой рабочий каталог.
Нужны разрешённые Python 3.9+, OpenSSH и CLI выбранных приложений в PATH.
Команда получает `connect.py` с доверенного SSH-сервера, сверяет SHA256 и запускает
его из временного каталога. Мастер получает `client.py` и сверяет второй SHA256.
Если появилось сообщение об ошибке SHA256, запросите у администратора актуальную строку.

Введите **1** для OpenCode, **2** для GigaCode или **3** для обоих. При первом входе
введите личный логин и пароль **Second Brain** в терминале. Пароль вводится скрыто.
Мастер сохраняет профиль, клиент и личный токен в `~/.silverbullet/ssh-mcp/`
(Windows: `%USERPROFILE%\.silverbullet\ssh-mcp\`). На Windows этот каталог должен
иметь личный ACL. Мастер проверяет вход и получает инструменты сервера, затем
вызывает штатный `mcp add` выбранного клиента. В запись `secondbrain` попадают
пути к Python, клиенту и файлу токена. Одноимённую старую запись CLI может
заменить. Редактировать JSON сотруднику не требуется.

### 4. Сотрудник проверяет работу

Откройте новую сессию агента. Проверьте `opencode mcp list` или `gigacode mcp list`
в зависимости от выбора. Если GigaCode показывает pending, проверьте команду и
подтвердите подключение по правилам организации. Попросите: «Через Second Brain
прочитай известную мне страницу и верни её название и ссылку». Если доступ
организован через роль `secondbrain`, поручите чтение этой роли. Её создают
по [инструкции сабагента](SECOND-BRAIN-SUBAGENT.md) при подготовке рабочего места.
Мастер регистрирует MCP и сохраняет действующие ограничения инструментов.

**Повторный запуск.** После смены версии на сервере повторите шаг 3: при отличии
локального клиента мастер предложит его заменить. Уже выданный токен используется
повторно. Для обновления истёкшего токена добавьте пробел и `--renew` в конец строки шага 3.
Если регистрация второго приложения не удалась, первый клиент мог уже сохраниться:
проверьте список и повторите шаг 3 для нужного приложения. После настройки при
обычном старте агент запускает локальный `client.py`; загрузка с сервера выполняется
только при запуске установщика.


## Справка по ручной настройке


При настройке MCP для рабочего агента сразу создайте отдельную роль
**secondbrain** по [SECOND-BRAIN-SUBAGENT.md](SECOND-BRAIN-SUBAGENT.md).
Основному агенту оставьте короткое правило делегирования; серверные правила
и навыки читает сабагент в своём контексте.

Возможность появилась в **offline-ssh-personal-20261116**, ядро
`2.12.1-offline.3+0fbe7b51`. Требуется новая серверная сборка: один bridge.py
не добавляет личные токены в прежний сервер. Корпоративная установка и
настройки клиентов при разработке не изменялись.

## Что происходит при входе

```text
OpenCode / GigaCode
  → локальный client.py: личный токен из конфигурации MCP
  → stdin зашифрованного SSH-соединения с общим ключом
  → серверный bridge.py
  → фиксированный 127.0.0.1:BACKEND_PORT/.ssh-mcp/rpc
  → проверка личного токена и текущих прав в SilverBullet
```

**Отдельная учётка агенту не нужна.** Токен выдаётся вашей существующей учётке
Second Brain. Он не создаёт пользователя ОС или нового пользователя приложения.
Учётка Second Brain может отличаться от корпоративного логина ОС — автоматического
SSO в этом пути нет. Права токена наследуются от его владельца.

По умолчанию клиент получает токен из настроек MCP-процесса. Keychain,
Credential Manager и Secret Service не открываются, их модуль не загружается.
Отсутствие токена вызывает ошибку без перехода к хранилищу ОС. Для выдачи токена
один раз используется `issue-token`: вводите логин и скрытый пароль Second Brain,
получаете приватный JSON-экспорт с токеном на 90 дней. Пароль не сохраняется.

Общий SSH-ключ даёт транспортный доступ. Автором запросов становится владелец
проверенного токена, независимо от SSH-логина и названия модели. На сервере
хранится SHA256 токена, его назначение, срок, версия учётных данных и имя
подключения. Имя имеет вид `SSH MCP PROFILE PROFILE_ID`; профиль на другом
компьютере получает другой ID. Оно помогает отзывать отдельные подключения,
но не доказывает, каким исполняемым файлом агента воспользовался человек.

Повторный `issue-token` (или явный нативный `login`) для той же учётки и профиля заменяет прежний токен. Смена пароля,
блокировка/удаление пользователя и отзыв токена прекращают доступ. Права
членства проверяются заново; токен не сохраняет прежние полномочия после их
снятия. После истечения 90 дней нужен новый `issue-token`; OAuth и автоматического
refresh в этом варианте нет. Старый публичный `/.mcp` продолжает использовать
OAuth для совместимости с прежними клиентами.

## Учётные записи и полномочия

Администратор создаёт каждому сотруднику отдельную **локальную** учётку Second
Brain без флага Admin и выдаёт ей `write` в нужном пространстве. Если ваша учётка
уже есть, повторно создавать её или заводить отдельного пользователя для агента не нужно. Одной учётке
оставляют Admin. Пароли индивидуальные; один пароль на команду уничтожает
персонализацию. SSO-вход для нового CLI-пути не реализован.

Личный токен работает только с приватным MCP, а не с общей HTTP API,
административной панелью или OAuth-endpoint. Через него доступны заметки,
поиск, ссылки и локальная Git-история в пространствах с правом записи.
Runtime/Lua недоступен. Прямую запись в `Library/`, `AGENTS.md`, `CONFIG.md`
через этот MCP разрешено делать только администратору; чтение правил доступно
сотрудникам. В текущем MCP пространства только с правом чтения не показываются.

Это ограничение личного MCP-токена. Прежняя браузерная роль `write` остаётся
доверенной ролью автора пространства и допускает редактирование библиотек и
активного содержимого. Изоляция произвольных скриптов заметок между недоверенными
авторами не добавлена. Для строгой роли «только контент» во всех интерфейсах
нужна отдельная доработка; инструкции модели сами по себе права не ограничивают.

## Подготовка на сервере

Нужны Linux-сервер с новой поставкой, Python >=3.9, работающий SSH и известный
оператору внутренний `BACKEND_PORT`. Стандартная новая обвязка запускает ядро
с `SB_SSH_MCP=1`; выключенные серверные настройки MCP всё равно запрещают вход.
При самостоятельном запуске ядра приватный маршрут по умолчанию выключен.
Не включайте его перед публичным прокси без проверки запрета `/.ssh-mcp`.

HTTP backend должен слушать **только 127.0.0.1**. Новый штатный шлюз возвращает
404 для всего `/.ssh-mcp`, включая нормализованные и кодированные пути.
Этот маршрут нельзя публиковать внешним reverse proxy. Bridge соединяется
только с фиксированным IPv4 loopback и не принимает URL назначения от клиента.

Оператор выбирает абсолютный `BRIDGE_DIR`. Допустим каталог внутри установки,
например `TARGET/ssh_mcp`, где новая поставка уже содержит bridge.py. Конфигурацию
можно хранить в `TARGET/config/ssh-mcp.json`; её сохранность нужно учитывать при
обновлениях. При размещении отдельно из проверенной поставки копируют
`ssh_mcp/bridge.py` и пример конфигурации в выбранный каталог. Имя bridge.json
ниже условное: передавайте действительный путь через --config.

Если текущее поручение запрещает менять TARGET, мост размещают отдельно.
Обязательного требования SSH/MCP держать его вне проекта нет. В конфигурации задают:

```json
{"backend_port": 12345}
```

`12345` — пример, его нужно заменить выбранным внутренним портом из действующего
config сервера. Файл не содержит секретов; права 0600 или 0644, владелец —
оператор/запускающий пользователь либо root; запись для группы/остальных запрещена.
Каталоги, bridge.py и конфигурация не должны быть доступны сотрудникам для записи.

Общий SSH-ключ должен быть ограничен **фиксированной командой моста**. Если он
даёт обычную shell или чтение данных/секретов серверной учётки, персональные
токены не создают границу доступа. Пример опции для отдельной записи authorized_keys:

```text
restrict,command="/usr/bin/python3 -I -B /ABSOLUTE/BRIDGE_DIR/bridge.py --config /ABSOLUTE/BRIDGE_DIR/bridge.json" ssh-ed25519 PUBLIC_KEY
```

Оператор подставляет свой Python, пути и публичный ключ. Нужен OpenSSH с
поддержкой `restrict`: без PTY, agent/X11/port forwarding и пользовательского rc.
При отдельной SSH-учётке также запретить forwarding в её серверной политике.
Не добавлять вторую неограниченную запись того же ключа. Строка — образец для
проверки оператором, клиент не меняет authorized_keys, sshd_config или firewall.
SSH-учётке не нужны users.json, ключ подписи приложения и произвольные команды:
достаточны запуск неизменяемого моста и соединение с backend.

Прежний `repair` обновляет только обвязку при совпадающем SHA256 ядра. Для
перехода с offline.2 на offline.3 он **откажет**. Не обходить эту проверку и не
переписывать manifest установленной системы: обновление существующего ядра с
резервной копией/откатом планируется отдельно. Перед откатом на offline.2 нужно
удалить личные `mcp-ssh` токены или восстановить согласованную резервную копию
учёток до их выдачи: прежнее ядро не знает ограничения нового назначения токенов. Новая установка проверяется по
[INSTALL.md](INSTALL.md); этот документ не разрешает заменять выбранный TARGET.

## Клиент без интеграции с хранилищем ОС

Для режима конфигурации достаточно **client.py** из `ssh_mcp/`; на сервере
нужен bridge.py прежней версии. Python >=3.9 и OpenSSH должны быть установлены
заранее. Pip/npm и загрузки при запуске не нужны. В релизе second-brain-20261117-r2
изменён только клиент: уже работающий сервер offline.3 обновлять не требуется.

Нужны согласованный SSH alias и проверенный ключ хоста в known_hosts. Клиент
использует StrictHostKeyChecking=yes, BatchMode=yes и отключает forwarding.
Интерактивную настройку SSH выполняют до подключения MCP; пароль приложения
не заменяет пароль SSH. Неизвестный ключ хоста клиент автоматически не принимает.

### 1. Профиль подключения

Задайте PYTHON — абсолютный путь к Python, CLIENT — абсолютный путь к client.py,
SSH_TARGET — согласованный SSH alias, REMOTE_BRIDGE и REMOTE_CONFIG — серверные
абсолютные пути. Если профиль team уже создан прежним клиентом, используйте его;
повторный configure не нужен и не перезаписывает существующий профиль.

```sh
"$PYTHON" -I -B "$CLIENT" configure --profile team \
  --ssh-target "$SSH_TARGET" --remote-bridge "$REMOTE_BRIDGE" --remote-config "$REMOTE_CONFIG"
```

Профиль содержит только имя, случайный ID, SSH alias и пути. По умолчанию:
macOS `~/Library/Application Support/SecondBrainMCP`, Windows
`%APPDATA%\SecondBrainMCP`, Linux `$XDG_CONFIG_HOME/secondbrain-mcp` либо
`~/.config/secondbrain-mcp`. Аргумент --config-dir, если он выбран, повторяется
во всех командах и в настройке MCP. Для другого сервера создайте другой профиль.
Для независимого отзыва OpenCode и GigaCode можно создать два профиля одной учётки.

### 2. Выпустить токен вашей учётки

TOKEN_EXPORT — новый абсолютный путь к приватному файлу вне проекта и Git,
например файл с суффиксом `.mcp-token.json` в личном каталоге конфигурации.
Каталог должен уже существовать и принадлежать вам, без записи для группы/остальных.

```sh
"$PYTHON" -I -B "$CLIENT" issue-token --profile team --username YOUR_LOGIN --output "$TOKEN_EXPORT"
```

Пароль вводится скрыто в вашем терминале. Аргументов для пароля/токена нет.
Если терминал не умеет скрытый ввод, клиент откажет. Реальные секреты не вводят
в чат агента, shell history и аргументы команд. Обычный API-токен из панели не
подойдёт: issue-token получает MCP-only токен `sbm_…` через зашифрованный SSH.

Команда создаёт только новый файл, никогда не заменяет config или прежний экспорт.
Токен не печатается в stdout. На POSIX файл получает 0600. На Windows файл
наследует ACL каталога: используйте личный каталог с ограниченным доступом;
проверка/изменение Windows ACL автоматически не выполняются. Если запись экспорта
не удалась после выдачи токена, клиент пытается отозвать его и сообщает, когда
отзыв не подтверждён. Не повторяйте вход вслепую при неопределённом результате.

В файле есть метаданные и объект `environment` с двумя значениями:
SECONDBRAIN_MCP_TOKEN — токен, SECONDBRAIN_MCP_PROFILE_KEY — привязка к этому
профилю и назначению. Переносите объект целиком. При несовпадении привязки клиент
откажет до запуска SSH. Не правьте привязку вручную для другого сервера.

Экспорт и конечный пользовательский config содержат секрет открытым текстом.
Они должны быть вне Git, с ограниченными правами (0600 на POSIX, личный ACL на
Windows). Не читайте их в контекст модели и не выводите debug config в журналы;
переносите значения редактором или механическим скриптом без печати содержимого.
В обязательных зеркалах/снапшотах соблюдайте те же ограничения: публичные копии
содержат только заглушки, секретные копии остаются приватными.

В PowerShell команды имеют те же параметры, с оператором запуска `&`:

```powershell
& $PYTHON -I -B $CLIENT issue-token --profile team --username YOUR_LOGIN --output $TOKEN_EXPORT
```

### 3. OpenCode 1.19.5: токен в пользовательском config

Объедините с существующим config **V1** следующий объект. В command нужны
реальные абсолютные пути: переменные shell внутри JSON не разворачиваются.
Замените оба COPY_FROM_PRIVATE_EXPORT значениями из environment экспорта.

```json
{
  "mcp": {
    "secondbrain": {
      "type": "local",
      "command": ["/ABSOLUTE/PYTHON", "-I", "-B", "/ABSOLUTE/CLIENT/client.py", "mcp", "--profile", "team", "--credential-source", "env"],
      "environment": {
        "SECONDBRAIN_MCP_TOKEN": "COPY_FROM_PRIVATE_EXPORT",
        "SECONDBRAIN_MCP_PROFILE_KEY": "COPY_FROM_PRIVATE_EXPORT"
      },
      "enabled": true
    }
  }
}
```

Клиент читает эти значения и передаёт токен по stdin внутри SSH. Перед запуском
SSH обе переменные исключаются из его окружения. Значение токена не попадает
в argv команды SSH. Новый режим не обращается к хранилищу ОС даже при ошибке.
Не оставляйте одновременно remote/OAuth-подключение с тем же именем.

На Windows используйте полные пути к python.exe и client.py с `\\` или `/`.
После настройки выполняют opencode mcp list и тест по SECOND-BRAIN-SUBAGENT.md.
Существующие запреты secondbrain_* и политика вызова Task не снимаются
автоматически; сохраняйте обязательные зеркала config без раскрытия секретов.
Схема V1 описана в [официальной инструкции миграции](https://opencode.ai/docs/migrate-v1#mcp-servers).

### 4. GigaCode 26.10.104

В настройке окружения **локального MCP-процесса** сохраните те же два значения
из environment экспорта. Конкретное поле и путь config сверяют с вашей сборкой:
закрытый CLI здесь не проверен. --header/--secret-header относятся к HTTP MCP
и не передают токен этому SSH-клиенту. Не вставляйте токен в `-e KEY=SECRET`
в shell-команде: тогда секрет окажется в argv и истории команд.

Есть готовый вариант без редактирования неизвестного поля окружения: использовать
приватный JSON-экспорт как файл конфигурации с токеном. В command сохраняется
только его путь; Keychain не используется:

```sh
gigacode mcp add secondbrain "$PYTHON" --transport stdio --scope user -- -I -B "$CLIENT" mcp --profile team --token-file "$TOKEN_EXPORT"
gigacode mcp list
```

Синтаксис add/stdio основан на предоставленной справке 26.10.104; если разбор
аргументов после -- отличается, сверить сохранённую команду с локальным help,
без перебора сетевых запросов. Pending-подключение проверяют перед approve.
--trust и OAuth для этого подключения не требуются.

### Файл вместо окружения и проверка наличия токена

Параметр --token-file поддерживается любым локальным MCP-клиентом, в том числе
OpenCode: добавьте его и путь экспорта в command вместо --credential-source env,
environment с секретом тогда не требуется. Файл читается только по явному пути;
автоматического поиска файлов и fallback к хранилищу ОС нет.

```sh
"$PYTHON" -I -B "$CLIENT" status --profile team --token-file "$TOKEN_EXPORT"
"$PYTHON" -I -B "$CLIENT" mcp --profile team --token-file "$TOKEN_EXPORT"
```

status проверяет наличие/формат токена и привязку профиля, **не сеть и не срок
действия на сервере**. В обычном shell переменные из config OpenCode/GigaCode
сами не появляются: status без --token-file может сообщить об отсутствии токена,
хотя клиент MCP настроен. Это не проверка подключения. MCP-команда предназначена
для запуска средой агента; в обычном терминале она ожидает JSON-RPC в stdin.

### Необязательный старый режим хранилища ОС

Только при разрешённой политике можно положить secret_store.py рядом с client.py
и явно выбрать --credential-source os-store. Например:

```sh
"$PYTHON" -I -B "$CLIENT" login --profile team --credential-source os-store
```

Тогда используется macOS Keychain, Windows Credential Manager либо Linux
Secret Service с заранее установленным secret-tool. Тот же флаг нужно указывать
при mcp/status/logout. По умолчанию этот модуль не загружается и никакие записи
в хранилище ОС не создаются и не читаются. При запрете Keychain этот режим
не используйте. Старая команда login без явного флага откажет и предложит issue-token.

## Правила записей, история и отзыв

После подключения создайте отдельного сабагента **secondbrain** по
[SECOND-BRAIN-SUBAGENT.md](SECOND-BRAIN-SUBAGENT.md). Основному агенту оставьте
короткое правило делегирования; правила и навыки он сам не загружает.
Сабагент сначала вызывает `help`, читает
`Library/Second Brain/Правила` и нужную процедуру через `help` с `topic`.
Создание, систематизация, шаблоны и `[[ссылки]]` описаны в
[KNOWLEDGE-SKILLS.md](KNOWLEDGE-SKILLS.md). Общие правила редактирует
администратор, обычный агент использует их для записей.

`read` возвращает ревизию; `edit`/замена существующей записи требуют актуальную
`ifRevision`. В конце согласованного изменения агент вызывает `git_commit` с
понятным сообщением. Администратор включает управляемую историю при установке;
при `history-mode disabled` истории нет. `git_history`, `git_diff`, `git_read`
помогают увидеть изменения; `git_restore` сохраняет историю и проверяет ревизию.

Автор снимка определяется сервером из личной учётки (имя профиля пользователя
или login). Дополнительно сервер дописывает в сообщение снимка
`SecondBrain-User: LOGIN` и `SecondBrain-Connection: LABEL` из проверенного
токена: смена отображаемого имени не скрывает login. Эти поля нельзя задать
в сообщении `git_commit` самому. При восстановлении файла такой же отпечаток
сохраняется в предварительном снимке, если есть изменения для снимка. Снимок охватывает всё пространство, включая ещё не сохранённые
в Git изменения других людей; автор снимка не доказывает авторство каждой
строки. Отдельного неизменяемого журнала каждого tool-call/каждой правки эта версия
не добавляет. Если новых изменений нет, Git-снимок не создаётся; это не журнал
всех вызовов. Администратор с доступом к Git может изменить историю.

Для отзыва токена из приватного экспорта:

```sh
"$PYTHON" -I -B "$CLIENT" logout --profile team --token-file "$TOKEN_EXPORT"
```

Сначала сервер подтверждает отзыв. Затем удалите значения из пользовательского
config и ненужные экспорты. Клиент эти файлы не редактирует; они будут содержать
уже недействительный токен. При потере связи отзыв не объявляется успешным и
повторов нет. Администратор также может удалить токен по метке подключения,
заблокировать учётку или сменить пароль. После истечения/отзыва токена выполните
issue-token с новым путём экспорта и обновите config. Повторная выдача для той же учётки и
профиля заменяет её прежний токен; другие профили не затрагиваются.

В явном os-store режиме logout после подтверждённого отзыва удаляет запись
из выбранного хранилища ОС. Новый режим конфигурации не обращается к старым
записям Keychain — их наличие не включает нативный режим автоматически.

Никаких повторов паролей, автопереподключения после неопределённого результата
записи и сетевого перебора клиент не делает. При ошибке остановиться и сообщить
оператору этап/тип ошибки без секретов. Прямые curl-пробы корпоративного сервера
и изменение сетевых ограничений не являются частью настройки.

## Что проверено

На Linux выполнен настоящий локальный SSH с фиксированной командой, одним
ключом и двумя пользователями: вход, initialize, список инструментов, правила,
чтение/запись/правка/поиск, отказ устаревшей ревизии, запрет правки Library,
Git-снимки с разными авторами и независимый отзыв. Трассировка всех потоков
ядра и потомков Git не обнаружила исходящих connect в этом сценарии.
В новом сквозном тесте реально проверены issue-token, приватный JSON-экспорт,
чтение переменных config и файла, CLI по умолчанию и отзыв. Хранилище ОС не
вызывается: тест прерывался бы при попытке его открыть. Сервер/SSH настоящие,
тестовые токены и пароли используются только в собственном временном каталоге.
Корпоративные клиенты OpenCode/GigaCode и нативные хранилища ОС ещё требуют
приёмки на рабочих местах; тест на VM её не заменяет.
