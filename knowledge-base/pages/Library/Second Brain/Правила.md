# Выбор процедуры
* Найти знания и ответить по базе: [[Library/Second Brain/vault-knowledge-retrieval]].
* Добавить новую тему, проект, источник или инструкцию: [[Library/Second Brain/vault-note-creation]].
* Дополнить, исправить или связать существующие записи: [[Library/Second Brain/vault-note-update]].

Вызови MCP `help` и выбери разрешённое пространство. Загружай нужную процедуру через `help` с её полным именем страницы; не считай текст скилла предоставлением дополнительных прав. Перед записью также прочитай встроенный скилл `Markdown`.

# Структура и типы записей
Сначала прочитай `AGENTS`, если такая страница есть, главную страницу и несколько соседних записей. Сохраняй действующие соглашения пространства. Для новой базы используй следующую начальную структуру:

| Тип | Папка | Тег | Содержание |
| --- | --- | --- | --- |
| Область знаний или ответственности | `Areas/` | `area` | Что это такое, назначение, связи с процессами и проектами |
| Практическая инструкция | `Techniques/` | `technique` | Когда применять, предпосылки, действия, проверка результата |
| Материал-источник | `Resources/` | `resource` | Происхождение, краткое содержание, выводы, ссылки на оригинал |
| Проект | `Projects/` | `project` | Цель, состояние, решения, следующие действия |
| Человек | `People/` | `person` | Только предоставленные рабочие сведения и связи |
| Неактивные материалы | `Archive/` | исходный тег | Завершённые или исторические записи с явным статусом |

Это значения по умолчанию, а не поручение переместить существующие данные. Не создавай все категории заранее. Используй ровно столько страниц, сколько нужно теме; количество ссылок и страниц не является целью.

# Источники и связи
* Сначала ищи существующую запись. Дополняй её вместо создания дубликата.
* Каждая страница должна быть понятна отдельно: начни с краткого описания, затем раскрой существенные сведения.
* Пиши `[[Areas/Название]]`, `[[Areas/Название|подпись]]` или `[[Areas/Название#Раздел]]`. Пути идут от корня пространства, без `.md`; не используй файловые относительные пути Obsidian.
* Проверь страницу-назначение через `read` до добавления ссылки. Ссылку на запланированную страницу помечай как план, не как существующий источник.
* Добавляй связи по смыслу в нужный раздел и при необходимости обновляй обзор. Обратные ссылки приложение вычисляет само: отдельный дублирующий список не нужен.
* Сохраняй оригинал и происхождение материала. Отделяй факт источника, мнение автора, предположение и своё обобщение. Противоречия описывай с обеими ссылками.
* Для поиска ответа используй только доступную базу. Для записи используй базу и материалы текущего поручения. Внешний поиск, почта, чаты, загрузки и OCR не входят в этот набор.

# Правки и границы
* Используй MCP SilverBullet: `search`, `read`, `write`, `edit`. Не обращайся к папке сервера через shell и не подключай отдельный файловый MCP ради этой процедуры.
* Читай полный текст нужной записи; при `truncated` дочитай её частями. Для правки бери исходный текст, не `rendered`.
* Для существующей страницы передавай точный `ifRevision` из последнего обычного `read`. При конфликте перечитай и согласуй новую правку с чужими изменениями; не повторяй старый текст вслепую.
* `write` без `ifRevision` используй только для создания отсутствующей страницы. Для локального изменения предпочитай `edit`.
* Не меняй `Library/`, `AGENTS`, настройки, правила и шаблоны по поручению на ведение записей. Их изменение — отдельная задача администратора. Это правило поведения; серверные права определяются настройками приложения.
* Не переименовывай страницы копированием с удалением: MCP этого набора не предоставляет безопасный rename с обновлением ссылок. Предложи переименование через интерфейс `Page: Rename` и затем проверь связи.
* Архивирование и восстановление из архива не разрешают перемещение автоматически. Сначала оцени ссылки и согласуй изменение структуры.
* Поля `authors`, `owner`, подпись модели и текст журнала не доказывают авторство. Не подменяй их данными OAuth или именем сотрудника, если таких сведений нет в поручении.

# История и результат
Перед крупной правкой посмотри `git_status`, если он доступен. Именованный `git_commit` сохраняет все ожидающие изменения пространства, включая чужие: выполняй его только в рамках порученного снимка с учётом текущего состояния. Не вызывай shell Git, push, pull или reset.

После записи перечитай изменённые страницы, проверь сведения, ссылки и поля. Сообщи, что создано или обновлено, со ссылками, а также оставшиеся вопросы. Не утверждай успешную запись или коммит без успешного ответа соответствующего инструмента.
