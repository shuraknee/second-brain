# Инструкция для человека: установка в выбранный каталог

Начните с этой страницы по ссылке из выбранного релиза. Используйте инструкции
и файлы именно его версии. Для установки через ИИ передайте ему ссылку на
[agent.md](agent.md) этого же релиза: агент сначала читает её в браузере.

Нужна текущая обезличенная офлайн-поставка с установщиком. Архив и SHA256
скачиваются заранее через разрешённый канал.
На сервере ничего скачивать или устанавливать из репозиториев пакетов не нужно.
strace не требуется: он используется только на машине испытаний. Встроенные
внешние транспорты исключены из этой сборки; ограничения и аудит описаны в
[OFFLINE-AUDIT.md](OFFLINE-AUDIT.md).

Поставка запускается двумя user-службами systemd, без Docker/Podman.
Namespaces, PrivateUsers/PrivateNetwork и изменение capabilities не нужны.
Сервер и Git наследуют обязательный seccomp-запрет connect; вход передаётся
через Unix-сокет. IPv6 включать не требуется: внутренний сервер использует IPv4.
При отключённом AF_INET6 самопроверка сообщает `unavailable:EAFNOSUPPORT`,
а проверки запрета IPv4 остаются обязательными.

## Входные значения

Оператор задаёт значения; при работе через агента — в своём поручении ему.
Значения ниже — обозначения,
а не готовые пути. TARGET может быть любым абсолютным новым/пустым каталогом,
доступным без sudo. SOURCE — отдельно распакованная поставка, не TARGET.

```sh
SOURCE='абсолютный путь распакованной поставки'
TARGET='абсолютный путь установки, выбранный пользователем'
PYTHON='полный путь установленного Python 3.9 или новее'
PORT='выбранный внешний порт'
LISTEN_HOST='IP сетевого интерфейса сервера для входящих подключений'
BACKEND_PORT='другой выбранный внутренний порт'
PUBLIC_URL='выбранный HTTP(S) origin без пути'
ADMIN_USER='выбранное имя администратора'
PLAN='полный путь нового файла плана вне TARGET'
```

Пробелы, кириллица, `%` и `$` в каталогах поддерживаются. Имя пользователя,
домашний каталог, диск и корень размещения проектов не предполагаются кодом.

## Проверка и план

После проверки SHA256 архива и отдельной распаковки:

```sh
"$PYTHON" -I -B "$SOURCE/tools/verify_payload.py"
"$PYTHON" -I -B "$SOURCE/tools/collect_environment.py"
"$PYTHON" -I -B "$SOURCE/tools/install.py" plan \
  --target "$TARGET" \
  --port "$PORT" --backend-port "$BACKEND_PORT" \
  --listen-host "$LISTEN_HOST" --public-url "$PUBLIC_URL" --admin-user "$ADMIN_USER" \
  --output "$PLAN"
```

Для входа с другого компьютера LISTEN_HOST — IP сервера, PUBLIC_URL — точный
`http://IP:PORT` для браузера. SSH-туннель не нужен. Допустим `0.0.0.0` как адрес
прослушивания всех IPv4-интерфейсов, но PUBLIC_URL должен содержать реальный IP
или DNS-имя, а не wildcard. CLI без --listen-host по-прежнему слушает 127.0.0.1.
Внутренний backend не публикуется. Открывать в браузере именно PUBLIC_URL:
посторонний Host отвергается шлюзом с 421. Доступность порта с рабочего места
проверяется отдельно; firewall и сетевые ACL установщик не меняет.

Для HTTP по обычному IP браузер отключает Service Worker и шифрование локального
кэша; ядро этой версии поддерживает онлайн-работу в таком режиме. HTTP не шифрует
передаваемые пароли и данные. Для HTTPS нужен заранее подготовленный TLS-прокси
и корректный PUBLIC_URL; сам ingress этой поставки TLS не завершает.

Plan проверяет реальную временную systemd user-unit с NoNewPrivileges
и seccomp-фильтр, включая его наследование дочерним процессом. Если ограничения ОС это запрещают, установка останавливается.
Менять политики или ослаблять профиль ради запуска нельзя.

`--no-start` добавляется к plan, если нужны только файлы/unit без запуска.
`--enable` — явный выбор автозапуска после login. Linger не изменяется.
Короткий socket-путь выбирается в XDG_RUNTIME_DIR независимо от длины TARGET;
при необходимости можно задать отдельный короткий `--runtime-dir`.

Локальная история включается по умолчанию (`--history-mode managed`): нужен
заранее установленный системный Git >=2.34. Plan/apply/start проверяют его
наличие; скачивания не выполняются. `--history-mode disabled` отключает историю
и требование Git. Инструменты агента и безопасное восстановление: [MCP-GIT.md](MCP-GIT.md).

## Применение

Проверьте сводку и SHA плана. Если установка с этими параметрами уже поручена,
дополнительное подтверждение не нужно. Иначе согласуйте конкретный готовый план.

```sh
PLAN_SHA256='значение PLAN_SHA256 из предыдущей команды'
"$PYTHON" -I -B "$SOURCE/tools/install.py" apply \
  --plan "$PLAN" --sha256 "$PLAN_SHA256"
"$PYTHON" -I -B "$TARGET/tools/install.py" status --target "$TARGET"
```

План/payload перепроверяются перед применением. Существующая установка и чужие
службы не заменяются. Сгенерированный config хранит все выбранные пути, unit
экранируются установщиком; ручная замена каталогов в шаблонах не требуется.
User-unit используют XDG_CONFIG_HOME — стандартную инфраструктуру systemd,
а не фиксированный путь самого приложения.

## Управление

```sh
"$PYTHON" -I -B "$TARGET/tools/install.py" status --target "$TARGET"
"$PYTHON" -I -B "$TARGET/tools/install.py" stop --target "$TARGET"
"$PYTHON" -I -B "$TARGET/tools/install.py" start --target "$TARGET"
```

Данные хранятся в TARGET/data. Начальный пароль — в data/initial-credentials.json,
права 0600; не публикуйте его. Уже установленный TARGET нельзя просто переместить:
его config и unit содержат выбранные при установке абсолютные пути. Для переноса
нужен новый план; изменения исходников проекта для другого TARGET не требуются.
Общее обновление/миграция в этой версии не реализованы; ограниченное исправление
прежней обвязки описано ниже.

START_OK подтверждает локальный HTTP, issuer и CSP. Вход, заметки, OAuth/MCP,
перезапуск и внешний HTTPS проверяются дополнительно по agent.md.

## Исправить существующую установку после CAPABILITIES/218

Для установок из offline-ipv4-only-20261110, offline-local-git-20261110 или
offline-plain-service-20261110,
у которых уже создана .install-state.json, использовать отдельную процедуру.
Обычный apply на непустой TARGET по-прежнему запрещён. Новый SOURCE должен
находиться отдельно от TARGET. PYTHON — тот же интерпретатор, что использовался
раньше. BACKUP — новый приватный каталог с существующим родителем вне TARGET,
каталога unit-файлов и runtime; REPAIR_PLAN — новый файл плана вне TARGET/backup.
Все пути выбирает оператор; значения старой установки читаются из её config.

```sh
"$PYTHON" -I -B "$SOURCE/tools/install.py" repair-plan \
  --target "$TARGET" --backup "$BACKUP" --output "$REPAIR_PLAN"
REPAIR_SHA256='значение PLAN_SHA256 из предыдущей команды'
"$PYTHON" -I -B "$SOURCE/tools/install.py" repair-apply \
  --plan "$REPAIR_PLAN" --sha256 "$REPAIR_SHA256"
"$PYTHON" -I -B "$TARGET/tools/install.py" status --target "$TARGET"
```

План проверяет хеши прежней поставки, владельца и точные собственные unit-файлы,
совпадение ядра и новый профиль user-службы. Apply перепроверяет план, останавливает
только эти службы, сохраняет прежние файлы поставки/config/unit/маркер в BACKUP,
заменяет обвязку и запускает службы с HTTP-проверкой. `--no-start` у repair-plan
позволяет оставить их остановленными. Пароли, учётные записи, заметки, Git-история,
порты и URL остаются на месте. Это исправление обвязки, не миграция ядра/данных.
BACKUP содержит прежние файлы поставки и приватный config, но не копию заметок.

При изменённых вручную unit-файлах, несовпадении SHA или незнакомой версии
процедура отказывает до остановки служб. После частичного сбоя сохраняются
BACKUP/repair.json и данные; агент должен изучить состояние, не запускать apply
вслепую и не удалять TARGET. На пустом TARGET используется обычный plan/apply.

## Сменить loopback/SSH-туннель на прямой вход по IP

На установленном предыдущем выпуске сначала выполнить repair из нового SOURCE
по разделу выше: это обновляет обвязку, включая CSP страницы MCP OAuth.
Для свежей установки текущего выпуска достаточно сразу выбрать LISTEN_HOST
и PUBLIC_URL в обычном plan. Не переустанавливать непустой TARGET.

После обновления обвязки использовать configure-plan/configure-apply.
TARGET — прежний выбранный каталог; LISTEN_HOST, PORT и PUBLIC_URL — новые
параметры браузерного входа. CONFIG_BACKUP — новый приватный каталог вне
TARGET/unit/runtime, CONFIG_PLAN — новый файл плана вне TARGET/backup.
Оба пути выбирает оператор. Старые backend-порт, данные и службы сохраняются.

```sh
"$PYTHON" -I -B "$SOURCE/tools/install.py" configure-plan \
  --target "$TARGET" --listen-host "$LISTEN_HOST" --port "$PORT" \
  --public-url "$PUBLIC_URL" --backup "$CONFIG_BACKUP" --output "$CONFIG_PLAN"
CONFIG_SHA256='значение PLAN_SHA256 из предыдущей команды'
"$PYTHON" -I -B "$SOURCE/tools/install.py" configure-apply \
  --plan "$CONFIG_PLAN" --sha256 "$CONFIG_SHA256"
"$PYTHON" -I -B "$TARGET/tools/install.py" status --target "$TARGET"
```

План проверяет владельца, хеши SOURCE/установки, согласованность config и
server.json, выбранный адрес и поддержку seccomp в user-службе. Apply
перепроверяет план, сохраняет configs в backup, останавливает только собственные
службы и проверяет порт после остановки. Меняются только listen_host,
listen_port, public_url и соответствующий primaryUrl в data/server.json.
Затем службы запускаются с HTTP/CSP/issuer-проверкой; `--no-start` у configure-plan
оставляет их остановленными. Заметки, пароли, Git, бинарник и unit-файлы не меняются.

При неудачном запуске прежняя согласованная пара configs восстанавливается,
службы остаются остановленными; изучить CONFIG_BACKUP/configure.json перед
повтором. Если остановка не подтверждена, автоматического отката нет — требуется
разбор журнала и состояния. После смены origin войти в браузере заново; MCP-клиенты
могут потребовать повторную авторизацию. Для проверки сети открыть PUBLIC_URL
с другого компьютера; локальная HTTP-проверка этого не заменяет.
