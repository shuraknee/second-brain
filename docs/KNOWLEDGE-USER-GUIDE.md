# Как работают инструкции Second Brain и как их менять

Набор включён в единую поставку `second-brain-20261117` и предназначен для работы через
MCP SilverBullet. Импорт в существующее пространство описан в
[KNOWLEDGE-SKILLS.md](../KNOWLEDGE-SKILLS.md).

## Как агент использует набор

1. Агент подключается к MCP под учётной записью сотрудника и вызывает `help`.
2. Сервер показывает доступные пространства, названия скиллов и короткие описания.
3. По задаче и описанию агент выбирает процедуру и читает её через `help` с `topic`.
4. Процедура объясняет, что искать, как выбрать страницу или шаблон, оформить
   ссылки и применить правку через `read`, `search`, `write`, `edit`.
5. Агент перечитывает результат и сообщает, какие страницы изменились.

Например, по поручению «сохрани порядок восстановления сервиса» агент должен
сначала найти существующую инструкцию. Если её нет — создать запись по шаблону
«Инструкция», добавить проверенные ссылки на связанные темы. Если запись уже
есть — обновить её с текущим `ifRevision`, сохранив чужие изменения.

| Страница | Для чего |
| --- | --- |
| `Правила` | Общие соглашения: структура, источники, ссылки и границы изменений |
| `vault-knowledge-retrieval` | Найти знания и ответить по прочитанным страницам |
| `vault-note-creation` | Создать запись, предварительно проверив дубликаты |
| `vault-note-update` | Дополнить или исправить существующую запись |
| `Templates/…` | Структура записей пяти типов |

## На что влияют описания

В начале страницы скилла есть YAML:

```yaml
---
tags: meta/skill
description: "Создать новую запись. Сначала проверить дубликаты; существующую тему обновлять через vault-note-update."
---
```

* `tags: meta/skill` позволяет SilverBullet обнаружить страницу как скилл.
* `description` объясняет агенту, **когда выбрать** этот скилл. Пишите конкретно:
  «обновить существующую запись», «ответить по базе», а не «помогает с данными».
* Текст после YAML объясняет, **как выполнить** работу: порядок действий,
  соглашения о ссылках, источниках и проверках.
* Шаблон задаёт разделы и начальные поля записи. Например, шаблон проекта
  предлагает цель, текущее состояние, решения и следующие действия.

Описание не выполняет команд и не гарантирует выбор процедуры моделью.
`help` не загружает тела всех скиллов автоматически. Права доступа и проверка
ревизий обеспечиваются сервером; текст инструкции не создаёт новых запретов.
В частности, просьба не менять настройки не заменяет серверное разграничение прав.

## Где всё хранится

Рабочая копия находится **в выбранном пространстве на сервере**, в папке
`Library/Second Brain/`. Это обычные Markdown-страницы:

```text
Library/Second Brain/
  Правила.md
  vault-knowledge-retrieval.md
  vault-note-creation.md
  vault-note-update.md
  Templates/
    Область.md
    Инструкция.md
    Источник.md
    Проект.md
    Человек.md
  Происхождение.md
```

Физический корень пространства смотрите в Dashboard → Space settings → General →
Folder. В wiki-ссылках и обычных MCP-вызовах имена страниц пишутся без `.md`,
например `Library/Second Brain/Правила`.

Исходная копия для поставки лежит в GitHub:
[knowledge-base/pages/Library/Second Brain](../knowledge-base/pages/Library/Second%20Brain).
Это отдельная копия: push в GitHub не обновляет уже работающий сервер,
а редактирование страницы сервера не отправляет её в публичный GitHub.

## Как править рабочие инструкции

1. Войдите в SilverBullet с правом записи и откройте дерево через команду
   `Navigate: Tree`. При необходимости выберите сегмент `Tool` для страниц `Library/`.
2. Откройте нужную страницу. Меняйте `Правила` для общих соглашений,
   `description` для условий выбора, тело скилла для процедуры, `Templates/…`
   для структуры новых записей. Сохраняйте тег `meta/skill` у скиллов.
3. Изменения сохраняются автоматически. После индексации повторный `help`
   должен показать обновлённое описание; прочитайте страницу через `help(topic)`
   для проверки полного текста.
4. Попросите уже работающего агента перечитать изменённые правила и нужный
   скилл. Прочитанный ранее текст в его контексте автоматически не заменяется.
   Для обновления списка шаблонов в браузере можно выполнить `System: Reload`.

Правка шаблона влияет на следующие создаваемые записи и не перестраивает старые.
При включённой истории изменения инструкций доступны через
`Revision: Page History`; подробнее — [MCP-GIT.md](../MCP-GIT.md).

Сейчас право `write` также позволяет менять эти страницы. Организационное правило
«инструкции меняет администратор» пока не является отдельной серверной ролью.
Корпоративные названия, сведения и правила сохраняйте в своём пространстве;
в публичный репозиторий отправляйте только предназначенные для публикации материалы.

## Как закрепить использование агентом

Добавьте в постоянные инструкции корпоративного клиента или дайте в начале работы:

> При работе с базой через MCP second-brain сначала вызови help и выбери
> пространство. Прочитай Library/Second Brain/Правила и подходящий скилл
> поиска, создания или обновления. Перед записью прочитай встроенный Markdown.
> Следуй действующим соглашениям базы, проверяй ссылки и используй ifRevision.

Эта инструкция одинакова по смыслу для OpenCode и GigaCode; она не требует
клиентских slash-команд из исходного набора Obsidian.

Повторный импорт поставки не заменит локально изменённые инструкции: он сообщит
`conflicts`. Обновление сравнивают и объединяют отдельно. Если меняете именно
публичный набор для будущей поставки, нужно обновить SHA256 страниц в
`knowledge-base/manifest.json`, проверить набор и выпустить новую версию по
[RELEASING.md](../RELEASING.md). Архивы уже опубликованного релиза не заменяются.

## Кто читает инструкции

Для повседневной работы используйте [отдельного сабагента secondbrain](../SECOND-BRAIN-SUBAGENT.md).
Основному агенту передаётся только правило делегирования. Сабагент сам читает
`Правила`, нужную процедуру и страницы через MCP; возвращает краткий итог со
ссылками. Это настройка клиента: push инструкции не создаёт роль автоматически
на компьютерах сотрудников и не меняет серверные навыки.
