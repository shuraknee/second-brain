# Правила сборки и выпуска Second Brain

Эти правила обязательны для всех следующих релизов, включая тестовые.
Существующие опубликованные архивы и теги не заменяются.

## 1. Сначала инструкции в браузере

Описание каждого релиза начинается с двух ссылок:

- **Для ИИ** — `agent.md`: агент сначала читает эту страницу в браузере и
  следует ей в пределах поручения пользователя.
- **Для человека** — `INSTALL.md`: параметры, команды установки и управления.

Ссылки ведут на `blob/<тег-релиза>/…`, а не на main/latest. Относительные ссылки
между инструкциями должны сохранять ту же версию. Обе инструкции обязательно
входят в runtime-архив и прикладываются отдельными Release Assets с SHA256.
Отдельные файлы должны побайтно совпадать с файлами внутри архива.
Release без этого комплекта публиковать нельзя.

Инструкция ИИ должна описывать получение параметров из текущего поручения,
проверку файлов, диагностику, plan/apply, приёмку и условия остановки. Путь TARGET
выбирает пользователь; имена серверов, учётные данные и пути разработчика
в инструкцию не вносятся. Передачу файлов и чтение страниц выполняют заранее
разрешённым способом; установка и запуск не должны требовать интернета.

## 2. Зафиксированные входные данные

- Использовать подготовленный локальный бинарник с SHA256 из manifest.json.
  Сборщик ничего не скачивает и не запускает SilverBullet.
- Перед новым выпуском назначить новый `supply_revision` в manifest.json;
  это же значение использовать как Git tag. Тег указывает на чистый коммит,
  содержащий код, обе инструкции и лицензии именно этого выпуска.
- Обновлять инструкции вместе с изменением параметров, требований и поведения.
  Проверять их соответствие фактическому CLI и ограничениям установщика.
- Смена бинарника/зависимостей требует обновления происхождения, SHA256,
  проверки совместимости и лицензионного комплекта по LICENSING.md.
- Для изменённого ядра соблюдать BUILD-OFFLINE.md и OFFLINE-AUDIT.md.
  Меняя код патча, обновлять встроенную версию ядра/клиента и epoch ресурсов,
  чтобы браузер мог отличить новую сборку от сохранённого service worker.
  Аудит исходников дополнять локальной трассировкой попыток; запрет соединений
  не выдавать за доказательство их отсутствия. strace — инструмент испытаний,
  а не обязательная зависимость установленной службы.

## 3. Состав и обезличивание

Runtime-архив собирается только по allowlist tools/build_supply.py. В него
входят бинарник, обвязка, шаблоны, пустой пример config, инструкции, эти правила, manifest,
лицензии/необходимые исходники компонентов и внутренний SHA256SUMS.
Отсутствующая или пустая agent.md/INSTALL.md блокирует сборку. MCP-GIT.md
поставляется внутри архива и отдельным asset с SHA256.
Владельцы и времена tar/gzip нормализуются; при тех же входных данных и
инструментах две сборки должны совпасть побайтно.

Исключать configs установки, планы, пароли, токены, данные заметок, SSH config,
диагностику, трассы, hostname, UID/GID и пути сборочной/целевой машины.
Оригинальные авторские имена и уведомления компонентов сохранять.
Пути бинарника, архива и каталога assets передавать явно; не фиксировать
каталог проекта, диск, пользователя или организацию в коде/дистрибутиве.

## 4. Проверки перед выпуском

В checkout с установленным Python >=3.9 и локальным bin/silverbullet:

```sh
"$PYTHON" -I -B tests/test_install.py -v
"$PYTHON" -I -B tests/test_package.py -v
```

Проверки должны подтвердить произвольные пути установки, защиту существующих
данных, совпадение состава/хешей архива, воспроизводимость, наличие инструкций
и блокирование подготовки релиза при их отсутствии, пустом содержимом или
расхождении с checkout. Лицензионные файлы проверяет сборщик.

При изменении runtime, изоляции или установки дополнительно проверить реальную
работу затронутого поведения в изолированном стенде, без ослабления защиты.
Отдельно проверить инструкции по CLI. В описании релиза указать выполненные
проверки, подменённые системные вызовы, ограничения и неподтверждённые условия.
Для изменений Git повторять локальные контрактные тесты под seccomp и MCP
сценарий по MCP-GIT.md, включая устаревшую ревизию, ссылки и перезапуск.
В сетевой трассе учитывать также дочерние процессы Git; hooks/filters/partial
clone не должны возвращаться в разрешённые конфигурации.
Проверка стенда не означает приёмку корпоративного сервера.

## 5. Подготовка Release Assets

Все переменные задаёт выпускающий: BINARY — локальный проверенный бинарник,
ARCHIVE — новый путь *.tar.gz, ASSET_DIR — новый каталог с существующим
родителем, REPOSITORY — GitHub OWNER/REPO, NOTES — локальный UTF-8 файл с
изменениями, результатами проверок и ограничениями. PYTHON — выбранный Python.
Эти команды выполняются без сети:

```sh
"$PYTHON" -I -B tools/build_supply.py --binary "$BINARY" --output "$ARCHIVE"
"$PYTHON" -I -B tools/prepare_release.py \
  --archive "$ARCHIVE" --output "$ASSET_DIR" \
  --repository "$REPOSITORY" --notes-file "$NOTES"
```

prepare_release.py проверяет внешний SHA256 и каждый файл payload, наличие
документов и совпадение инструкций/manifest с checkout. Он берёт документы
из проверенного архива, создаёт отдельные SHA256, общий SHA256SUMS и
RELEASE_NOTES.md с двумя ссылками на инструкции в теге supply_revision.
Существующий каталог assets не перезаписывается. Репозиторий передаётся только
для генерации ссылок; инструмент ничего не загружает в GitHub.

## 6. Публикация

После проверок закоммитить изменения, проверить чистоту checkout и создать
тег из manifest. Сначала создать черновик релиза в правильном репозитории.
Включить **все файлы ASSET_DIR**; описание взять из RELEASE_NOTES.md, сохранив
две начальные ссылки. Проверить, что тег уже существует и указывает на нужный
коммит. Кандидат/экспериментальный выпуск помечать prerelease.

На стадии публикации разрешён сетевой доступ к хостингу. Скачать все assets
черновика обратно, сверить SHA256 и побайтное совпадение с ASSET_DIR, проверить
внутренний SHA256SUMS и обе ссылки на инструкции. Просмотреть описание и
публикуемые файлы на сведения об окружении. При расхождении остановить выпуск.
Публиковать только после успешных проверок и выполнения LICENSING.md.

После публикации проверить доступность инструкций и скачивание архива без
авторизации, если репозиторий публичный. GitHub Source code содержит исходники
обвязки; для установки требуется runtime-архив из Release Assets.
Исправления выпускаются новым тегом/архивом, а не подменой опубликованных файлов.
